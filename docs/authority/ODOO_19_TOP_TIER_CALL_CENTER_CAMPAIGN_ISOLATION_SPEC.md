# Odoo 19 Enterprise Contact Center Campaign-Isolation Specification

## Top-tier operating model for Odoo 19 + VICIdial + Asterisk + Codestra Middleware + n8n + Klyrow/Postal + AI

> **Status:** Architecture and Codex implementation authority.  
> **Release posture:** STAGING-ONLY. All live dialing, live lead publication, production agent synchronization, external email delivery, provisioning, IVR activation, callbacks, and recording playback remain disabled until the formal production gates in this specification pass.  
> **Scope:** This document replaces the Odoo-side operating model while preserving the cross-system campaign inventory and trust boundaries of `VICIDIAL_ODOO_MAPPING_SPEC.md`.

## Normative language

`MUST`, `MUST NOT`, `REQUIRED`, and `PROHIBITED` are binding. `SHOULD` is a strong default that may be changed only through a documented architecture decision and security review.

---

# 1. Executive objective

Build Odoo 19 as the enterprise contact-center business system of record for eight business units, with a hard security boundary around every campaign. The implementation must give each campaign its own workspace, users, supervisor, email routes, CRM/helpdesk records, lead lists, scripts, dispositions, callbacks, recordings, quality records, dashboards, transfer routes, SLAs, workflows, and integration mappings.

The design must operate like a top-tier multi-campaign contact center while enforcing these non-negotiable rules:
* An agent has exactly one active Campaign Workspace membership.
* An agent can log into, view, search, receive, export, report on, email from, call from, or transfer within only that one campaign.
* An agent can never select or switch to another campaign, even by changing a URL, RPC payload, browser context, API request, email thread, report filter, record ID, or VICIdial login parameter.
* Each active human-staffed campaign has exactly one active primary supervisor. A supervisor is assigned to exactly one campaign.
* The overall Global Contact Center Administrator is the only operational role with full cross-campaign administration.
* Each campaign has its own email aliases and distribution membership. Agents receive only messages generated by or routed to their campaign.
* Every disposition set is owned by one campaign and version. Even universal outcomes are cloned into each campaign-owned set; no selectable global disposition list is shared across campaigns.
* Every live transfer stays inside the source campaign. Cross-campaign live transfers are rejected.
* Odoo never writes directly to VICIdial tables. VICIdial, n8n, browsers, and AI never write directly to Odoo business tables or VICIdial tables.
* Codestra Middleware remains the only operational integration gateway; the accepted VICIdial adapter is the only dialer write path.
* All sensitive actions are least-privilege, auditable, idempotent, reversible where possible, and protected by feature flags.

# 2. Systems of authority and trust boundaries

| System | Authority | May do | Must not do |
| --- | --- | --- | --- |
| Odoo 19 | Business records, campaign hierarchy, desired agent state, CRM/helpdesk, scripts, disposition definitions, callbacks, QA, workforce, compliance, reporting | Publish desired state and receive normalized events through middleware | Write VICIdial tables or trust browser-supplied campaign scope |
| VICIdial / Asterisk | Telephony sessions, dialer execution, queues, raw call logs and native recording metadata | Execute approved telephony configuration and calls | Create business truth or allow cross-campaign agent access |
| Codestra Middleware | Only operational integration gateway | Authenticate, authorize, validate mapping, enforce idempotency, route commands/events, audit | Invent campaign mappings or bypass Odoo/VICIdial authorization |
| Server B VICIdial Adapter | Accepted dialer mutation and read-back component | Apply validated desired state and return evidence | Accept direct browser, Odoo, n8n, or AI writes |
| n8n | Asynchronous automation | Consume signed events and request approved middleware commands | Write directly to Odoo/VICIdial tables or decide authorization |
| Klyrow / Postal | Email transport | Send and receive campaign-addressed mail through signed routes | Determine campaign ownership from untrusted message content |
| AI services | Assistive summaries, QA suggestions, knowledge retrieval | Produce recommendations with source and confidence | Dial, transfer, disposition, suppress, approve, or mutate authoritative records directly |
| Browser clients | Odoo same-origin user interface | Perform actions authorized by the active Odoo session | Call VICIdial administrative APIs or choose arbitrary campaign IDs |

The integration path is:

```text
Agent browser
  → Odoo 19 same-origin session
  → Codestra Middleware for telephony commands
  → authenticated Server B adapter
  → VICIdial / Asterisk

VICIdial events
  → Server B adapter
  → Codestra Middleware normalization, idempotency and audit
  → Odoo outbox/inbox consumers
  → n8n / AI only from signed, scoped events
```

# 3. Identifier correction and compatibility contract

The readable identifiers in the source mapping remain the canonical Odoo codes, but they cannot always be used verbatim in VICIdial. Codex must implement an explicit mapping rather than truncating values silently.

| Object | Canonical Odoo identifier | Native VICIdial constraint | Required implementation |
| --- | --- | --- | --- |
| Campaign | Example `COD-WEB-OUT` | `vicidial_campaigns.campaign_id` is 8 characters | Store the long code in Odoo and map it to an explicit unique 8-character dialer ID such as `CODWEBO` |
| Disposition | Example long label `Discovery Complete` | Native status code is 6 characters; display name is separate | Use a <=6-character code such as `DISCOV` and retain the full label in Odoo |
| Script | Versioned Odoo code may be long | Campaign script identifier is 10 characters | Use an explicit <=10-character dialer script ID plus an immutable Odoo script/version record |
| VICIdial user | Odoo employee/user identity | Dialer username is 20 characters | Use a stable non-email dialer username and retain external identity mappings |
| User group | Long descriptive group name | Native user-group ID is 20 characters | Use a short technical ID and a long Odoo display name |
| Inbound group | Long descriptive queue name | Native inbound-group ID is 20 characters | Use a short technical ID and map it 1:1 to the campaign workspace |

The complete 93-channel canonical-to-native mapping is delivered in `odoo_vicidial_campaign_identifier_matrix.csv`. Codex MUST load this mapping as controlled seed data and MUST fail validation when a collision, overlength ID, missing mapping, or duplicate external ID is found.

# 4. Enterprise contact-center hierarchy

```text
Global Contact Center Administrator
│
├── Compliance Officer / Auditor          (separate duties; controlled read/hold authority)
├── Quality Assurance Analyst             (scoped recordings and evaluations; no CRM outcome edits)
├── Workforce / Real-Time Analyst         (schedule and queue metrics; PII minimized)
├── Campaign Configuration Manager        (draft configuration; controlled publication)
│
└── Campaign Workspace
    ├── Exactly one Primary Supervisor
    ├── Senior Agent / SME                 (same record scope as agent; no supervisor authority)
    └── Campaign Agents                    (exactly one campaign membership each)
```

## 4.1 Scaling rule

A campaign may never gain a second active supervisor merely because headcount grows. When operational span exceeds the approved capacity, split the workload into isolated campaign pods, for example `COD-WEB-A` and `COD-WEB-B`. Each pod receives its own supervisor, lists, users, aliases, dispositions, callbacks, reports, and transfer groups.

## 4.2 Acting-supervisor rule

A campaign may have a pre-approved backup person, but only one person may hold active supervisor authority at a time. A time-bounded acting-supervisor grant MUST:
* reference an incident, leave, or change ticket;
* set explicit start and expiry timestamps;
* suspend the primary supervisor's operational supervisor grant for the same interval;
* revoke all sessions and recalculate email/queue memberships at activation and expiry;
* notify the Global Contact Center Administrator and Compliance;
* write immutable grant and revocation audit events.

# 5. Campaign Workspace: the unit of isolation

A Campaign Workspace is the only scope an agent understands. It represents one business purpose and contains only the approved inbound, outbound, callback, support, closer, appointment, and email routes for that same purpose.

Required Campaign Workspace fields:
* `id`, immutable UUID
* `code`, long canonical code
* `business_unit_id`
* `company_id`
* `environment`
* `active` and `lifecycle_state`
* `primary_supervisor_membership_id`
* `odoo_crm_team_id`
* `odoo_helpdesk_team_ids`
* `vicidial_campaign_mapping_ids`
* `default_list_mapping_ids`
* `user_group_mapping_ids`
* `inbound_group_mapping_ids`
* `transfer_route_ids`
* `script_set_id` and active version
* `disposition_set_id` and active version
* `email_route_ids`
* `recording_policy_id`
* `callback_policy_id`
* `consent_policy_id`
* `calling_time_policy_id`
* `quality_program_id`
* `workforce_policy_id`
* `reporting_policy_id`
* `feature_flag_set_id`
* `scope_version`, incremented on every security-relevant change

## 5.1 Mandatory ownership fields

Every campaign-owned business model MUST inherit a common campaign-scoped mixin and store:

```text
company_id
business_unit_id
campaign_id
environment
external_id / integration_key
active
scope_version
created_by / created_at
updated_by / updated_at
```

The `campaign_id` field is required, indexed, immutable to agents, and validated against the user's active membership on every create and write.

## 5.2 Defense-in-depth scope

* Menu visibility is scoped, but menus are never the security boundary.
* Action domains and default contexts are scoped, but client context is never trusted.
* ACLs define permitted operations by role.
* Global record rules enforce campaign scope for every ORM read/write.
* Model constraints prevent campaign mismatch between related records.
* Database partial unique indexes enforce one active campaign per agent and one active supervisor per campaign.
* Middleware revalidates campaign, user, target group, external IDs, and feature flags before every telephony command.
* VICIdial user groups allow only the mapped campaign and mapped inbound groups.
* Email routing, bus notifications, chatter, attachments, activities, exports, and reports inherit the same campaign scope.

# 6. Role catalog and separation of duties

| Role | Scope | Primary authority | Prohibited |
| --- | --- | --- | --- |
| Campaign Agent | One campaign | Work assigned/queued contacts, calls, callbacks and campaign mail | Campaign switching; user management; configuration; cross-campaign data; recording search; bulk export |
| Senior Agent / SME | One campaign | Agent duties plus assigned peer-support/coaching tasks | Supervisor dashboards, membership changes, silent monitoring, QA finalization |
| Campaign Supervisor | One campaign | All campaign operations, queue oversight, approved monitoring, escalations, coaching and schedule exceptions | Other campaigns; global configuration; changing signed QA results; assigning self as second supervisor |
| QA Analyst | Assigned campaign QA scope | Sample, score, calibrate and create coaching recommendations | Changing dispositions, CRM stages, financial decisions, user memberships or scripts |
| Workforce / Real-Time Analyst | Assigned campaign metrics or de-identified aggregate | Forecast, schedule, adherence and real-time queue management | Full customer notes, documents, recordings, payments or underwriting content |
| Compliance Officer | Policy scope | Consent, DNC, disclosure, retention and hold controls | Selling, funding, dispositioning as an agent or altering QA evidence |
| Campaign Configuration Manager | Assigned campaign configuration | Draft scripts, dispositions, aliases, SLAs and mappings | Publishing own high-risk change without approval; live dialing activation |
| Global Contact Center Administrator | All campaigns | Overall configuration, access governance, incident response and approved break-glass | Unlogged access, self-approval where two-person control is required |
| Technical Administrator | Platform only by default | Module, infrastructure and deployment maintenance | Business-data access except time-bounded break-glass |
| Auditor | Approved read-only evidence | Audit, reconciliations and release evidence | Operational writes |

No single role may both prepare and approve a high-risk access or production-activation change. User provisioning, campaign publication, production dialing activation, recording-policy changes, DNC removal, and financial-policy changes require separation of duties.

# 7. Membership and identity lifecycle

## 7.1 Odoo records

Create `cc.campaign.membership` with:
* `user_id` and `employee_id`
* `campaign_id` and `business_unit_id`
* `role`
* `state`: draft, pending_approval, active, suspended, expired, revoked
* `starts_at` and `ends_at`
* `is_primary_supervisor`
* `approved_by` and `approved_at`
* `source_ticket`
* `keycloak_subject`
* `vicidial_user` and mapped user group
* `campaign_email_identity` and distribution groups
* `scope_version`
* `last_sync_status` and read-back evidence

## 7.2 Database invariants

Codex MUST add migration-managed partial unique indexes equivalent to:

```sql
CREATE UNIQUE INDEX cc_one_active_agent_campaign
ON cc_campaign_membership (user_id)
WHERE state = 'active' AND role IN ('agent', 'senior_agent');

CREATE UNIQUE INDEX cc_one_active_supervisor_per_campaign
ON cc_campaign_membership (campaign_id)
WHERE state = 'active' AND role = 'supervisor' AND is_primary_supervisor;

CREATE UNIQUE INDEX cc_supervisor_one_active_campaign
ON cc_campaign_membership (user_id)
WHERE state = 'active' AND role = 'supervisor';
```

Equivalent application constraints are also required so users receive a clear Odoo validation error before the database rejects an invalid transaction.

## 7.3 Provisioning transaction

```text
Approved Odoo membership
→ calculate desired Keycloak/Odoo/email/VICIdial state
→ write transactional outbox event
→ middleware validates campaign mapping and feature flags
→ Server B adapter provisions VICIdial user/group
→ email adapter applies campaign mailbox/distribution membership
→ read-back every target
→ Odoo marks synchronized only after all required read-backs match
```

Partial provisioning is not active access. The membership remains `pending_sync` or `blocked` until required systems reconcile.

## 7.4 Campaign reassignment

Reassignment is a controlled revoke-then-grant operation, never an in-place campaign switch:
1. Approve the destination assignment and effective time.
2. Pause the agent and prevent new calls.
3. Log the agent out of VICIdial and revoke active Odoo/SSO sessions.
4. Remove old campaign email and queue memberships.
5. Close or reassign old campaign work without exposing destination records.
6. Revoke the old membership and increment scope version.
7. Provision the new campaign membership.
8. Read back Odoo, SSO, email, middleware and VICIdial state.
9. Allow login only after reconciliation passes.

# 10. Odoo security implementation rules

## 10.1 Fail-closed rule design

Odoo access rights and record rules must be designed as a complete set. Record rules are default-allow after ACL access is granted when no applicable rule restricts the record, so Codex must not rely on scattered group-specific rules. Campaign-owned models require a global fail-closed campaign rule plus narrowly scoped role capabilities.

Required pattern:

```xml
<record id="rule_cc_global_campaign_scope" model="ir.rule">
    <field name="name">Contact Center: global campaign scope</field>
    <field name="model_id" ref="model_cc_example"/>
    <field name="global" eval="True"/>
    <field name="domain_force">
        [('campaign_id', 'in', user.cc_allowed_campaign_ids.ids)]
    </field>
</record>
```

For every campaign-owned model, Codex MUST prove:
* agent `search`, `search_read`, `read`, `name_search`, `read_group`, `export`, `copy`, `create`, `write`, and `unlink` cannot cross scope;
* direct record-ID access is rejected;
* related-field traversal cannot reveal another campaign;
* computed fields do not use unrestricted `sudo()`;
* mail, activity, attachment, portal, report and bus-notification access is equally scoped;
* global admin access is explicit and audited, not accidental superuser leakage.

## 10.2 ORM and `sudo()`

* Raw SQL is prohibited in user-facing business paths because it bypasses ORM security.
* `sudo()` is prohibited for agent/supervisor business operations unless a narrowly reviewed service method re-applies campaign authorization before and after elevation.
* Public methods must not accept a campaign ID as authority. They derive campaign scope from the authenticated user's active membership.
* Context keys such as `allowed_company_ids`, `campaign_id`, `active_id`, `search_default_*`, and web-route parameters are treated as untrusted input.
* Integration service users have dedicated groups, model allowlists, client credentials, IP/mTLS controls, and no interactive login.

## 10.3 Field security

| Field class | Agent | Supervisor | QA/Compliance | Global admin |
| --- | --- | --- | --- | --- |
| Campaign identity | Read; immutable | Read; immutable | Read | Controlled change workflow |
| PII | Minimum needed for assigned work | Campaign need-to-know | Masked unless policy requires | Audited |
| Financial/underwriting decision | Customer-facing status only | Customer-facing status only | Policy-specific read | Restricted full access |
| Disposition result | Create for own call; correction by workflow | Approve campaign correction | Read only | Audited override |
| Recording URL/storage key | Never exposed directly | Short-lived authorized playback | Short-lived authorized playback | Audited |
| DNC/consent | Can capture request/evidence | Can review | Can hold/release per policy | Administer policy |
| User membership | No | No direct changes | No | Approved governance workflow |

# 11. Login, SSO and session pinning

* Authentication uses the approved OIDC provider. Identity claims authenticate the person but do not by themselves authorize a campaign.
* At login, Odoo resolves exactly one active operational membership for an agent or supervisor. Zero or multiple memberships deny the contact-center session.
* The active campaign ID and `scope_version` are stored server-side. Browser-supplied campaign values are ignored.
* Agent landing route is `/contact-center/agent`; supervisor landing route is `/contact-center/supervisor`. Campaign-specific vanity login routes may exist only as hints and must be validated against membership.
* Every RPC/controller method rechecks active membership and scope version. A stale version forces logout and reauthentication.
* Campaign reassignment, suspension, supervisor delegation, password reset, security incident, or deactivation revokes Odoo, OIDC and VICIdial sessions.
* Agents cannot open Settings, Contacts, global CRM, global Helpdesk, generic reporting, external API tokens, Studio, developer mode, or user/group administration.
* VICIdial provisioning sets `change_agent_campaign=0`, disables unauthorized campaign selection, allows only the mapped campaign/user group/inbound groups, and disables unneeded reports/exports.

# 12. Campaign email and omnichannel isolation

Each campaign receives its own inbound aliases, outbound sender identity, supervisor address, distribution groups, templates, signatures, SLA rules, and quarantine policy.

Recommended alias classes:

```text
<campaign>.leads@<configured-domain>
<campaign>.sales@<configured-domain>
<campaign>.support@<configured-domain>
<campaign>.billing@<configured-domain>
<campaign>.callbacks@<configured-domain>
<campaign>.supervisor@<configured-domain>
<campaign>.qa@<configured-domain>
```

Not every campaign enables every alias. Enabled aliases are declared in `cc.mail.route` and mapped to one campaign.

## 12.1 Inbound flow

```text
Klyrow / Postal
→ signed inbound adapter
→ Codestra Middleware
→ validate recipient alias, tenant, campaign, thread token and replay key
→ Odoo campaign mail-ingest service
→ create/update only the mapped campaign record
→ notify only active campaign members allowed by routing policy
```

## 12.2 Hard email rules
* An alias determines campaign scope server-side; sender subject/body headers cannot override it.
* An existing thread token that points to another campaign is quarantined and never auto-merged.
* Agents are members of only one campaign distribution set.
* Agents do not receive global catch-all, all-sales, all-support, all-agents, or all-campaign mail.
* Outbound `From`, `Reply-To`, signature, legal footer and tracking domain are campaign-controlled.
* Chatter followers are campaign-scoped. Cross-campaign followers are rejected.
* Attachments are malware-scanned, type/size validated, campaign-tagged and access-controlled.
* Bounce, complaint, unsubscribe and DNC signals update only the correct campaign policy scope and are audited.
* Supervisor escalation messages go only to the campaign's one active supervisor; global security incidents additionally notify the Global Administrator/Compliance.

The Odoo agent workspace must be a focused desktop, not the standard unrestricted backend.

Required panels:
* authenticated campaign identity and immutable campaign badge;
* agent state, shift and pause-code controls;
* current call and queue state from normalized realtime events;
* campaign customer profile and verification checklist;
* active approved script with version and required disclosures;
* campaign knowledge articles;
* lead/ticket fields appropriate to the campaign profile;
* same-campaign transfer options only;
* callback and appointment controls;
* campaign-owned email thread;
* disposition form with required fields and wrap-up timer;
* supervisor-help request;
* personal performance view limited to the agent's own data.

The desktop must not expose campaign selectors, generic global search, unrestricted contacts, global activity feeds, other teams, other agents' customers, raw recording storage links, or administrative dialer controls.

The one campaign supervisor receives a campaign-only control center with:
* real-time agents, state, queue depth, longest wait, service level, abandon rate and callback backlog;
* campaign lead/ticket backlog and SLA breaches;
* same-campaign transfer and escalation status;

# 16. Campaign-owned scripts

* Every campaign has its own script set, even when initially cloned from a common template.
* Scripts are immutable versions. Editing creates a new draft version.
* Approval requires author and approver separation for regulated or high-risk scripts.

# 17. Disposition architecture

Disposition design is campaign-owned, typed, versioned, and workflow-driving.

## 17.1 Mandatory rules
* Every campaign has exactly one active disposition-set version.
* A disposition-set record cannot be attached to more than one campaign.
* Universal outcome definitions are cloned into each campaign-owned set, preserving isolation.
* VICIdial status codes are at most six characters; Odoo stores the full label and behavior.
* Agents see only statuses enabled for their campaign, channel, direction, role and current call state.
* Free-text notes never replace a disposition.
* Required fields are enforced before call wrap-up completes.
* Each outcome maps to an Odoo stage, next activity, callback behavior, suppression behavior, reporting category, n8n event and reconciliation rule.
* `DNC` executes immediate campaign/entity suppression through middleware and cannot be delayed by a follow-up workflow.
* Disposition correction uses a separate request/approve workflow; original values remain in audit history.
* Duplicate event delivery is idempotent and produces one effective Odoo outcome.
* A call without a valid final disposition enters an exception queue and blocks silent completion.

# 18. Callbacks and appointments

A callback belongs to one campaign forever. It cannot be reassigned across campaigns.

The eight source-specification `*-CALLBACK-OUT` records are retained only as disabled technical compatibility mappings. They are marked `agent_login_allowed=FALSE`, may not pool work from multiple Campaign Workspaces, and are not human-staffed campaigns. Normal scheduled callbacks must execute in the source campaign's native callback facility and return to agents from that same campaign. Codex must not create a shared callback-agent team from these compatibility records.

Required fields:
* campaign, business unit and environment;
* VICIdial lead ID and Odoo customer/lead/ticket ID;
* source call unique ID;
* callback type: customer-specific, agent-specific, queue, appointment, transfer recovery;
* assigned agent or campaign queue;
* customer time zone and local scheduled time;
* reason, priority, consent state and preferred channel;
* attempt count, last result and next action;
* appointment ID if applicable;
* middleware idempotency key and VICIdial read-back.

Flow:

```text
Agent schedules campaign callback in Odoo
→ Odoo validates campaign, time zone, consent, calling hours and required fields
→ outbox event
→ middleware validates mapping and feature flags
→ Server B adapter publishes callback to mapped campaign
→ read-back
→ reminders via n8n/Klyrow
→ APPT_PREP or callback-ready state
→ same campaign agent receives work
→ final disposition and Odoo completion
```

Missed, overdue and failed callbacks enter the same campaign supervisor's recovery queue. They never move to a global callback team visible to other campaigns.

# 19. Recordings, quality and coaching

## 19.1 Recording model
* VICIdial/Asterisk remains the source of raw recording creation.
* Odoo stores metadata and a protected object-storage reference, not unrestricted media binaries.
* Each recording is bound to one campaign, call unique ID, agent, customer profile, policy version and retention state.
* Storage objects use encryption, checksum, malware validation where applicable, immutable metadata and short-lived signed playback URLs.
* Agents have no general recording library. A campaign policy may allow an agent to replay a specifically assigned coaching sample.
* Supervisor and QA playback is campaign-scoped, purpose-bound and logged.
* Payment-card or other prohibited data must not be retained in recordings; use pause/resume, secure IVR, tokenized payment links or approved redaction.
* Legal hold overrides normal deletion but never expands access.
* Deletion is policy-driven, evidenced and reconciled with storage.

## 19.2 Quality program
* Campaign-specific scorecards and critical-fail questions;
* risk-based and random sampling;
* new-agent enhanced sampling;
* calibration sessions with versioned outcomes;
* evaluation acknowledgement and dispute workflow;
* coaching plan with owner, due date, evidence and effectiveness review;
* separate QA author and finalizer where required;
* no editing of signed evaluations—corrections create superseding versions;
* campaign-only QA dashboards plus de-identified global aggregate.

# 20. Transfer and referral rules

## 20.1 Allowed live transfer

A live transfer is allowed only when source campaign, destination group, destination agent, customer profile, call, script, compliance state and transfer policy all belong to the same Campaign Workspace.

Examples:

```text
COD-WEB workspace agent
→ COD-WEB closer
→ COD-WEB support
→ COD-WEB supervisor
```

## 20.2 Prohibited live transfer

```text
COD-WEB
→ COD-AI
→ MoneyBee
→ any other campaign or business unit
```

Middleware returns a fail-closed rejection, records `cc.transfer.rejected.v1`, and shows the agent a safe explanation without exposing destination staff or records.

## 20.3 Controlled cross-campaign referral

When a customer genuinely requests another service, use an asynchronous `cc.referral`, not a live transfer. The referral:
* captures explicit customer consent and requested destination;
* shares only the minimum approved fields;
* is created by a privileged middleware service;
* creates a new destination-campaign record without giving the source agent access;
* provides the source campaign only a non-sensitive referral status;
* does not add the source agent as follower or recipient in the destination campaign;
* is idempotent, audited and suppressible.

* Calling hours are evaluated in the customer's local time before dialing.
* Consent source, text/version, timestamp, number/channel and revocation state are retained.
* Predictive or automated outreach capabilities remain disabled until campaign-specific legal and operational approval.
* AI-generated or prerecorded voice use is separately capability-gated.
* Payment-card details, security codes, bank credentials and authentication secrets are prohibited in notes, chatter, email, logs and recordings.
* Use secure payment links, approved IVR/payment providers, tokenization and recording pause/resume.
* Sensitive MoneyBee underwriting and financial data use field-level groups, minimum necessary display and access logging.
* Bulk exports are disabled for agents and supervisors by default; approved exports are encrypted, expiring and audited.
* Retention and deletion policies are versioned per record type and campaign, with legal hold support.

# 27. Audit, observability and evidence

Audit events are append-only and include:
* login success/failure and campaign-scope denial;
* membership request, approval, activation, suspension, delegation, expiry and revocation;
* campaign configuration draft, approval, activation and rollback;
* script/disposition/template/policy changes;
* record reads of high-risk models and all recording playback;
* exports, bulk actions and report downloads;
* call, transfer, callback, DNC, consent and disposition actions;
* email routing, quarantine, bounce, complaint and unsubscribe;
* break-glass request, approval, use and expiry;
* integration commands, responses, retries, read-backs and drift;
* production-gate approvals and feature-flag changes.

Observability MUST expose campaign-safe metrics, structured logs, traces, correlation IDs, dead-letter queues, drift alerts and reconciliation status. Secrets, full PII and recording URLs are never logged.

# 28. Mandatory test suite

## 28.1 Cross-campaign negative tests
1. Agent A cannot log into Campaign B.
2. Agent A cannot read Campaign B by direct ID.
3. Agent A cannot find Campaign B through search, name search, grouped reporting, autocomplete or global search.
4. Agent A cannot create a record with Campaign B in RPC/context.
5. Agent A cannot change an existing record's campaign.
6. Agent A cannot see Campaign B chatter, followers, activities, attachments or bus notifications.
7. Agent A cannot receive Campaign B email or appear in its distribution group.
8. Agent A cannot open Campaign B recording metadata or playback URL.
9. Agent A cannot schedule or claim Campaign B callback.
10. Agent A cannot transfer to Campaign B group/agent.
11. Agent A cannot export Campaign B or obtain aggregate counts that reveal it.
12. Supervisor A cannot see or administer Campaign B.
13. QA/WFM roles cannot exceed their expressly assigned data classes.
14. Technical admin cannot see business data without active break-glass.
15. A stale session is denied immediately after membership/scope-version change.
16. Multiple active agent memberships fail.
17. A second active primary supervisor fails.
18. An overlength/colliding VICIdial identifier fails validation.
19. An email thread/alias campaign mismatch is quarantined.
20. A duplicate call/disposition event creates one effective outcome.

## 28.2 Positive integration tests
1. Create synthetic campaign and one agent/supervisor; provision and read back all systems.
2. Login redirects to the correct campaign workspace.
3. Campaign lead/email/call screen-pop is visible to the correct agent.
4. Same-campaign transfer succeeds and preserves context.
5. Cross-campaign transfer is rejected and audited.
6. Callback publishes once, is read back, routed to the same campaign and completed.
7. Recording metadata reconciles; authorized playback works; unauthorized playback fails.
8. Disposition enforces required fields and triggers exactly one workflow.
9. DNC blocks future campaign dialing before the next call command.
10. Supervisor dashboard reconciles to VICIdial logs.
11. Deactivation logs out the agent and revokes all campaign access.
12. Rollback restores the prior approved configuration without enabling production.

## 28.3 Odoo-specific CI gates
* module installation and upgrade from prior supported state;
* uninstall safety only where modules are designed to uninstall;
* PostgreSQL constraint and migration tests;
* ACL and record-rule matrix tests for every campaign-owned model;
* controller/RPC authorization tests;
* mail.message, mail.activity and ir.attachment isolation tests;
* no forbidden `sudo()` or raw SQL in scoped paths;
* idempotent outbox/inbox and replay tests;
* schema/data-file validation;
* lint, type checks where used, dependency and secret scan;
* coverage on security-critical code and mutation/negative testing;
* generated mapping-catalog drift check.
